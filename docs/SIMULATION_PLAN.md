# Simulation and test campaign (owner order, 2026-10-08)

Owner's words: build a complete, real-feeling SIMULATION on this laptop, with the exact code and database schema/data that are live; test rigorously: all options and variations, multiple cancellations, changing dates, Playwright, real Chrome, a local WhatsApp, at least 10 runs, 50 games beginning at the same time and ending in various ways; find gaps, fix them locally, test again; only then deploy to live. This is a simulation, not real: nothing may touch the live site, real e-mail, real WhatsApp, real Razorpay or real Google.

## Hard safety rules (every agent)
- NEVER send a request to the live site (corporate-tambola.pages.dev) except the one read-only parity check in step 1 (GET of public files) and the read-only D1 export that the lead runs. NEVER run `tests/e2e/run-live.mjs` (it switches the live site to TEST mode). NEVER call wrangler with deploy, secrets or write commands.
- The simulation server runs in TEST mode with no RESEND/Razorpay/Google credentials: e-mails are captured (not sent), payments are labelled test payments, Google uses a fake key set, the public randomness beacon (drand) is faked, WhatsApp is the local simulator.
- Ports: sim server 8801, WhatsApp simulator 8890, fake beacon in-process; never 8799 (the owner's demo server may be running there).
- Laptop has 8 GB RAM: at most 6 Chrome contexts at once, large crowds run through the bun phone-runtime simulator (no browser). Take `C:\ct\heavy.lock` only after checking that no other `bun test` is running; remove stale locks from agents that finished.

## The pieces

1. **Parity proof** (`node tools/sim2/parity.mjs`): (a) schema: live migrations list vs apps/edge/migrations vs the local copy (`sqlite_master` of the exported live DB vs the SCHEMA constant); (b) code: build pages (`pages/build.mjs`) and compare SHA-256 of every file against the same file fetched from the live site (read-only GETs; clean URLs map .html); report any file that differs; (c) worker: record the git commit and a hash of apps/edge/src; the Pages deploy id. Output `docs/SIM_PARITY_REPORT.md`.
2. **Live-copy database**: the lead exports the live D1 read-only to `data-backup/live-export.sql` (git-ignored); the agent imports it into `sim/live-copy.sqlite` (git-ignored), makes `apps/edge/src/local.ts` (or a new `tools/sim2/server.ts`) able to start on an EXISTING database (today it fails with "duplicate column name: jr" because the SCHEMA ALTERs are not idempotent: fix that in the local runner only, not in production code) and run the exact Worker code. Sealed personal data in the copy cannot be opened (live DATA_KEY is not here): the simulation creates its own organizations/games next to the live rows to prove compatibility with real existing rows.
3. **Controllable clock**: `tools/sim2/server.ts` wraps the Worker's `handle(req, env, now)` with `now = Date.now() + offset`, and a local-only `/__sim/clock` endpoint (set, advance, freeze); for Playwright use the page clock API so the browser agrees with the server; scenarios can jump hours or days (reschedule, late payment, 23 h erasure, 365-day purge, cron ticks every simulated minute via the same lifecycle tick the cron Worker calls).
4. **Fake beacon**: deterministic randomness per round that browsers and the bun phones accept (intercept the drand URLs in Playwright; inject `beacon` deps in the phone-runtime) so a whole game can run in seconds of real time.
5. **WhatsApp simulator** (`tools/sim2/whatsapp/`): a local web app at :8890. Playwright intercepts `https://wa.me/**` and `https://api.whatsapp.com/**` and redirects to it; it shows a chat with the number, the pre-filled message, a SEND button (like real WhatsApp, nothing is sent until pressed); on send the message lands in that number's inbox (`GET /api/inbox/<number>`), and the recipient's "phone" (a Playwright mobile context) can tap the link in it. Records every message for assertions.
6. **E-mail capture**: a sink that records every e-mail the Worker would send (subject, to, text) for assertions and for a viewer page.
7. **Scenario library** (Playwright with real Chrome `channel:'chrome'` for UI flows; bun phone-runtime for crowds), randomised by seed:
   - Organizer: sign-up (e-mail code, Google fake), create/edit all ten steps, all prize houses and max winners, Unlucky, brand + logo, brand moments, lucky draws, rounds 1 to 5, gap 9/12, own number of players, Who can join list/anyone, guest invites 1 to 10, preview, publish, Pay (test payment, double click, pay link, confirming state), Copy payment link.
   - Team: Hosts (email only/mobile only/both, first open, e-mail code, Google fake, expired link, new link), Co-hosts, limits, retire, Host cannot add Hosts, Co-host cannot do X (full permission matrix against docs/Corporate_Tambola_Roles_and_Rules.xlsx).
   - People: contacts picker (stub), paste, CSV, personal links via the WhatsApp simulator, common link + list match, first-wins duplicates, over-limit, waiting room (admit, decline, approve all, who approved), remove before/during, forwarded personal link, level 1/level 2 rules.
   - **Money policy (spec 6): NO REFUNDS.** Cancelled paid game -> credit for 365 days; use credit in full / partly (top-up) / remainder; two credits; credit expiry at the end of day 365 (IST) with e-mails (cancel, 30 days, 3 days, use, lapse); payment after cancel -> credit; credit isolated per organization; no Razorpay refund call exists.
   - **Data policy, every clock** (time-travel through each): guest data erased 23 h after the game ends (within 24 h), unplayed games erased 23 h after the scheduled end, rescheduled games follow the new time, 'bring my people list' clone moves the list, Co-host details with guests, Organizer/Host data and payment/invoice records kept until day 365 and then purged, settings of an unplayed game kept 30 days, drafts 30 days, credit lapses at the end of day 365, backups statement, e-mails only to Organizer/Host (heads-up 6 h before, after-erasure), report link lifecycle (3 min after the end, reminder 6 h before closing, closes at 22 h).
   - Cancellation: unpaid/paid, before/after start, three confirmations (cancel at each stage, 'No' at each stage, checkbox gate), multiple cancels, cancel twice, cancel then pay (refund path), Host cancels (Organizer e-mail), cancelled screens on every surface, erasure after cancel.
   - Dates: reschedule earlier/later, 30-day limit, past dates refused, late payment (+2 min start), unpaid hold messages (Organizer/Host vs everyone else), expiry and erasure at end + 23 h, reuse/clone ('Create a new game like this one' once built), 365-day purge.
   - Play: crowds of 10 to 300 phones, late joiners, offline phones, identical winners everywhere, one ticket one phone, pause/resume/stop, announcements, brand strip, removed phones keep winners stable.
   - Money: checkout validation, webhook signature (fake secret), idempotency, refunds with fee, credit notes, partner commission void, pay link states.
   - Abuse/security: cross-organization access, AI-key limits, role gates, rate limits, malformed input, brand/logo injection, CSP.
   - Pages: every public page and the console at 360/768/1280/1920 (overflow, text size, console errors) with screenshots.
8. **Campaign runner** (`node tools/sim2/campaign.mjs --runs 10 --seed 1`): each run (a) resets the sim DB from the live copy, (b) runs the scenario library with that run's seed, (c) launches **50 games at once** (varied size, start times staggered within the same minute, mixed outcomes: finish, cancel mid-way before start, unpaid hold, rescheduled, paid late, removed phones) through the bun phone simulator plus 3 to 6 real-Chrome games, (d) checks invariants (every phone sees the same winners, per-house maxima, no ticket twice, nobody paid twice, erasures on time, no personal data left after erasure, no e-mail to anyone but Organizer/Host), (e) writes `docs/SIM_RUN_<n>.md` (pass/fail, timings, D1 write counts against the free-plan budget, gaps found). Ten runs minimum, in the end all green.
9. **Gaps**: every finding goes into `docs/SIM_GAPS.md` (id, what, how to reproduce, severity, fix status). Fixing is done serially by one fixer at a time on the local code with a test for each gap; after each fix the affected suites re-run; the whole campaign re-runs at the end.
10. **Then deploy**: only when the final campaign run is clean, the full unit suite and tsc pass, and the parity report shows local == what will be deployed. The lead deploys (migrations first, then Pages), then re-runs the parity check against live and publishes URLs for every role.
