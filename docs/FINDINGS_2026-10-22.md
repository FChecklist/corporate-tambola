# Findings from the release B testing (2026-10-22)

Plain words, for the owner. Each item says what was found, whether it is fixed, and what it means for a real game.

1. **"End the game" / "Pause" could not reach phones if the organizer never opened the console before the start.** Phones used to stop checking for pause/stop messages 60 seconds after the start when no pause key existed (the console registers that key when a game is built or opened there before the start). A game built entirely through the AI link, with the console first opened during the game, showed "Stop sent" while the phones carried on. Found by scenario S23-05. **Fixed (release B):** phones now keep checking once a minute after the start, so a key registered late reaches every phone within about a minute and Pause / End the game work; a first attempt to refuse late keys on the server was dropped because it broke legitimate flows. Proof: phone-runtime test "a key registered AFTER the start still reaches a phone within about a minute", and S23-05 in Chrome.
2. **A phone offline for more than about three minutes across an "End the game" carries on from the public numbers on its own** (by design: a lost organizer cannot freeze a room) and can show prizes from numbers after the stop until it reconnects. Accepted trade-off; not changed. The organizer's own list of winners (the store) is the one that counts for handing prizes over.
3. **Players never see earlier numbers or the board; the organizer alone has the board** (/board.html, opened from the console). Verified in Chrome (S18-02, S18-04).
4. **Many winners per prize and the two tie rules** verified in Chrome with 5 phones (S18-02, S18-03); the store names the winner of each position only by an opaque ticket id, never a name or number.
5. **Exceptions verified:** the public clock unreachable from a phone for a minute (S23-01), the store answering "busy" for a while (S23-02: claims are sent later exactly once), two consoles editing the same draft (S23-03: the later save wins, nothing breaks), the same number joining from a fresh browser (S23-04: no second ticket, told calmly it is on another phone).
6. **The player's ticket must stay on the first screen of a phone.** The first version of the live prizes list sat between the number ball and the ticket and pushed the ticket below the fold on 320 to 375 px phones (S11-03). Fixed: the ticket comes first, the prizes list after it.
7. **Built in release C (live 2026-10-22 22:05 IST, commit 3b1e168): the real-housie play mode is now THE mode.** Players tap each called number themselves and press Claim before the next number; the software checks every claim; a wrong claim is a Bogey and two Bogeys on a prize put the ticket out of that prize (docs/GAME_PRINCIPLES.md). Proof: unit 2,105 / web 450 / Chrome 198 scenarios green on the committed tree.

## Real-site test (2026-10-22, corporatetambola.com itself, not a simulator)

The owner asked for the real website to be tested with 100 participants, in both calling modes, plus the demo, with the price set to zero only for the test window (`FREE_LAUNCH`), and all test data deleted afterwards. Tool: `tools/livetest/live.mjs` (a fresh organizer account, 100 people on the list with personal links, 94 joined through the API, 6 real headless Chrome phones that tap and claim, the organizer's console, board and number screen; everything on the public site with the real public random numbers and the real store).

8. **Demo game (10 people, free): passed end to end** - published free, 11th person refused, 4 real phones joined through the page, played to the end by claiming, every phone agreed on the winners, the store held the same winners, the organizer could read the claims and Bogeys, no JavaScript error. One phone saw 88 numbers and another 89: a phone stops listening the moment it hears the last prize was claimed (known, harmless).
9. **Auto mode, 100 people: passed end to end (second run, 13 of 13 checks).** The first run showed the store 2 winners behind the phones at the instant the test closed the browsers. Cause: only a fifth of the phones report a result at first and the rest join wave by wave (every 30 s) if the store still lacks it; in this test 94 of the 100 seats were API dummies that never open a page, so the 6 real phones were the late waves, and the test closed them within seconds of the end. Phones that stay open keep reporting after the end (they did: the second run's store caught up within 55 s). Not a product fault in a real game, where every seat has a phone and 20 of 100 report within 4 seconds. The test now waits for the store before judging.
10. **The free-launch switch did not work from the Cloudflare dashboard.** The Pages project deploys with `pages/wrangler.toml`, which has its own `[vars]` block, and Cloudflare then ignores dashboard variables of the same kind. `FREE_LAUNCH` had to be put in the toml for the test window and removed again afterwards (verified by `/api/payments/status`: `freeLaunch` true during, false after). Recorded in `docs/PROTECTION.md`'s sibling note and the memory file so nobody repeats it.
11. **Console after a game (cosmetic, seen on the real site):** after a reload the "numbers called" figure fills progressively from the public beacon (60 / 90 for ~15 s, then the full figure); and the "Next:" hint still said "Date and time of the game" once the game was over. The hint is fixed in this release ("The game is over. Hand over the prizes from step 9 ..."); the progressive count is left as is.
12. **Host mode, 100 people: passed.** The organizer's console pressed "Next number" 85 times; 84 numbers were released (numbers came only on presses), all 8 prizes were won by claiming, every phone agreed, the store matched the phones within 61 s, claims and Bogeys readable, no JavaScript error. Two harness notes, not product faults: 8 of 94 API joins (done at one per second) got a non-JSON answer from the edge and were counted as failed (a single join a minute later worked; the harness now retries once, as a phone would), which is also why the "101st refused" check could not trigger; and the console reloaded by the harness 4 s after the end still showed "Loading..." - it takes longer than 4 s to load after a 100-person game (the harness now gives it longer).
13. **Clean-up done:** every test game's participants erased (10 + 100 + 100 + 100 + 100 + 96 rows), `FREE_LAUNCH` removed and redeployed; the test organizer account (a plus-address of the owner's own e-mail, holding only empty game shells) is closed by `cleanup --close` once the server's "a game is running" window of the last host-mode game ends (one hour after the last press - by design, so a Host who pauses for an hour does not lose the game) (`/api/payments/status` shows `freeLaunch:false`), the saved test token deleted. No price, payment or deletion rule was changed.
